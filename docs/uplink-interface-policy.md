# 上联网卡选择

桌面和服务器的每个 Core 实例单独配置用于建立隧道的上联网卡。配置同时用于 IPv4/IPv6 地址发布、源地址选择、STUN、直连及反向打洞；不会修改系统路由、防火墙或其他 VPN 配置。

默认自动识别：

```toml
[uplink]
mode = "auto"
```

手动指定允许使用的网卡：

```toml
[uplink]
mode = "manual"
interfaces = ["eth0", "eth1"]
```

Windows 使用系统中的完整网卡名称，例如 `interfaces = ["Ethernet 2", "Wi-Fi"]`。名称精确匹配；允许名称内部的空格，不允许空名称、首尾空白、控制字符和重复项。手动模式必须至少指定一个接口；自动模式不能同时保留手动名单。

Web 控制台及桌面客户端的“节点参数 → 网络接口 → 上联网卡选择”提供相同配置。手动名单每行一个接口。切回自动模式会清空名单；中央管理的成员配置通过现有保存、下发及实例重建流程生效。成员覆盖重置会恢复默认自动模式。控制台与受管 Core 均需使用支持该配置的版本，旧 Core 不会执行新增配置。

## 选择与故障处理

- Linux 根据设备类型、硬件及下层链路关系识别正常上联，允许虚拟机的 virtio/VMXNET 网卡及能追溯到正常上联的 bridge、bond、VLAN，排除 WireGuard、TUN/TAP、veth 和仅由容器设备组成的桥。
- 无法可靠区分物理拨号与 VPN 的 PPP 接口应手动指定。手动名单也可用于选择其他有意使用的逻辑上联。
- Windows 结合系统接口类型、隧道属性、硬件标志和适配器描述筛选；macOS 使用平台接口规则，并在发送时约束实际接口。
- 正常上联网卡上的私网 IPv4 和 IPv6 ULA 保留，不按地址段直接排除。链路本地、回环、多播及不可用的 IPv6 地址不作为对端候选发布。
- 手动名称不存在时报告配置错误；名单中已知接口临时掉线时，可使用其他仍可用的允许接口。全部不可用时失败，不回到未允许的 VPN 网卡。
- `prefer_ipv6` 保持独立：优先使用允许上联中可用的 IPv6；IPv6 不可用时可继续使用允许集合内的 IPv4。此配置不增加缺失的 IPv6 地址或运营商路由。

UDP 使用固定绑定允许网卡的 socket，并指定所选源地址。TCP 主动连接在连接前固定接口；受约束的 TCP 监听在握手前绑定允许接口。Linux/macOS 的接口监听可继续接收该接口更新后的地址；Windows 的 TCP 监听绑定具体本地地址，地址变化后需要重新创建实例。UDP 路由选择缓存短暂保留，发送失败即失效。

此配置仅用于支持原生接口约束的桌面和服务器：Linux、Windows、普通 macOS。Android、iOS、macOS Network Extension（`macos-ne`）及 OHOS 不启用此策略；移动端的 Wi-Fi、蜂窝网络和切换由操作系统选择。它们保持既有系统选网行为，直接向不支持的 Core 下发显式手动策略会返回不支持错误。

本地 Android/iOS 客户端完全隐藏上联网卡选择及接口名单。编辑导入的旧配置时，客户端会移除本地旧 `uplink` 设置，TOML 预览、校验和保存使用同一结果，不修改其他配置字段。移动客户端使用远程管理模式时，配置属于远端 Core，仍保留远端网卡选项及已有策略，不根据查看端的系统或屏幕大小屏蔽；远端是否支持由目标 Core 校验。Web 控制台同样不根据浏览器设备类型推断目标节点能力。

Android VPN 插件按实际安装包名排除自身流量，兼容改包名的客户端；此项不等同于手动指定 Wi-Fi 或蜂窝接口。

本地打洞控制报文、普通 DNS 解析、代理转发及面向 TUN 的 RPC 保留各自的路由语义。Web 的公网共享 TCP/UDP 配置监听使用自动上联策略；它不属于某个普通成员的手动名单。Compact/WASI Host 保留配置供管理读回，但不会宣称执行原生网卡选择；未实现的平台保持既有自动行为并拒绝不支持的显式手动配置。

Linux 网络命名空间的地址及运行状态按当前线程读取。若命名空间继承了其他命名空间的 sysfs 挂载且设备元数据不一致，自动识别会保守拒绝；此时可在目标命名空间内使用手动名单。

仅有 veth 上联的容器同样需要显式指定容器内网卡，例如 `interfaces = ["eth0"]`。自动模式不会因为容器中存在默认路由，就将任意软件网卡判定为物理上联。

同一进程、同一网络命名空间内，不同实例的固定监听端口必须互不冲突。原生 Host 为逻辑监听器保留端口所有权，网卡 backing socket 共享其所有权，避免 `SO_REUSEPORT` 将不同实例的报文混在一起。IPv4 和 IPv6-only 监听仍可共用同一数字端口；实例停止并释放 socket 后可以重新使用该端口。

## 验证

配置测试覆盖 TOML、管理 JSON/Protobuf 往返、手动到自动的重置及成员覆盖持久化。原生隔离实验使用独立网络命名空间、允许上联和模拟 VPN 优先路由，验证 IPv4/IPv6 UDP/TCP、禁止源地址/接口、反向 TCP 及 IPv6 丢失后的 IPv4 可用性。

实验入口为 `easytier/src/socket/uplink_lab_tests.rs`，需要 `CAP_NET_ADMIN`、Linux 的 `unshare/nsenter/ip` 工具和隔离启动器；普通测试不会执行其中的网络变更：

```sh
cargo test -p easytier --lib --no-run
python3 script/test-uplink-netns.py --test-binary /absolute/path/to/target/debug/deps/easytier-TEST_HASH --proof /tmp/uplink-lab-proof.json
```

启动器只在临时命名空间中配置接口、路由及实验所需的反向路径检查，不修改宿主网络；退出时清理实验进程。有 tcpdump 时还会验证允许的测试流量没有从模拟 VPN 接口发出。Windows 的实际 VPN 建链仍需设备验证。Android/iOS 的聚焦浏览器测试验证本地隐藏控件、旧配置编辑与保存恢复系统选网；这些是界面及载荷测试，不代表移动设备实机建链测试。
